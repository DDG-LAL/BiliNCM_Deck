# Companion 队列状态机移植记录

旧 `BiliNCM-Companion.ps1` 的完整队列状态机已移植为 C#：

```text
src/BiliNCM-Deck/CompanionQueueEngine.cs
```

网易云 `track_queue` 是唯一播放顺序；bot 的 `_targetQueue` 只是点歌请求收件箱。5566 浮层读取引擎生成的快照，不再直接推导队列。

## 已实现的状态机

每条点歌请求在引擎里保存为 `KnownItem`：

- `IsD`：是否为点歌请求
- `State`：`Legacy / New / Upgrade / Pending / Playing / Done`
- `PendingQid`：该请求在 NCM 中对应的精确队列 wrapper
- `Seq`：FIFO 序号
- `Absent / BotAbsent`：NCM / bot 队列连续缺失次数
- `RetryAt`：移动或加入失败后的重试时间
- `ReRequested`：播放中或待播中再次被点

轮询顺序与旧 Companion 一致：

1. 读取 bot 队列增量（首次启动把已有队列标记为 `Legacy`）
2. 读取 NCM 当前歌、`track_queue`、当前索引和 wrapper
3. 合并重复点歌；已播过的歌再次点会进入 `Upgrade`
4. 检测 bot 队列撤回：加入 NCM 前撤回则取消；待播 d 从 bot 队列消失后停止跟踪
5. 按 NCM 队列校正 `Pending / Playing / Done`
6. 处理播放结束、wrapper 变化、待播副本被手动删除
7. 网易云重启后等待页面/队列稳定，再按 `Seq` 恢复真正缺失的待播 d
8. 每轮最多执行一次 add/move，失败按 2/5/10 秒重试

## 关键语义

- 当前歌曲永远不打断，也不移动
- 新点歌插在最后一个 pending d 之后；没有 pending d 时插到当前歌之后
- 重复点歌不新增副本；主播置顶/置顶点歌会把目标放到当前歌下一首，连续置顶以最后一次排最前
- 只有 `PendingQid` 精确匹配的那一项才会显示为待播 d
- 主播手动拖动/删除/插入优先，引擎不会把顺序改回去；显式“置顶”命令是例外，会主动移动到当前歌下一首
- 网易云重启时不会把已播历史误判成待播
- 旧 bot 的普通点歌/撤回/队列删除仍作为请求入口，由状态机跟随其结果，不再被新 Deck 另写一套 NCM 操作
- 强制插队/强制播放已删除；切歌仅主播和房管可用
- `关闭点歌` 只拦截新的普通点歌；`开启点歌`、管理命令和待播撤回在暂停时仍可用
- 撤回当前播放歌曲仅主播/房管可用；普通观众只能撤回自己的待播请求
- A/B 同歌重复点歌时，撤回/移除只取消自己的请求；NCM 副本在最后一条请求消失时才删除

## 与旧 Companion 的实现差异

- 不再起独立 PowerShell 进程，也不再轮询 `/data`；引擎直接读取进程内的 bot 队列快照。
- 不再写 `overlay-state.json`；5566 `/state` 直接返回引擎快照。
- 轮询间隔、状态、重试次数和 add/move JS 与旧 Companion 保持一致。
- 原 5555 API 已迁移到 5566，5555 监听和旧队列 UI 已移除。

## 已验证

在真实网易云 2.10.13 + CDP 9222 上验证：

- 当前歌播放中点新歌，当前歌 id/播放状态不变
- 新歌插入当前歌之后；第二首排在第一个 pending d 之后
- 同一首重复点，队列长度不变、顺序不变
- 手动从 NCM 删除待播项后，引擎在连续缺失判定后移除浮层行
- 再次点已从 NCM 消失的歌，会重新升级为待播 d
- 杀掉并重启网易云后，重启前的待播点歌会按序恢复
- CDP 已就绪时不会重启网易云；缺少 CDP 时才按 `ncm-path.txt`/进程路径启动

## 仍需真实直播回归

## 风险

- NCM 2.10.13 的 `defPlayer.MF` / store 结构可能变化
- 手动换歌单会替换 `track_queue`，引擎不会强行回填旧 pending
- 同一首歌被不同人重复点时，元数据保留最早的点歌人
